Why Convert JSON to TypeScript?

Every modern application speaks JSON. APIs return it, configuration files are written in it, databases store it, and logs are full of it. JSON is flexible and universal, but inside a TypeScript codebase that flexibility becomes a liability the moment you start guessing at shapes. You write response.data.user.address.city, the editor offers no autocomplete, a rename slips through unnoticed, and a field that was a number last month quietly arrives as a string. Converting a real JSON payload into TypeScript interfaces turns those guesses into a contract. The compiler checks every access, the editor completes every property, and refactors that touch a shared type surface everywhere it matters. ModelMint exists to make that conversion instant: paste a genuine sample of the data you actually receive, and receive interfaces that describe it faithfully.

Hand-writing interfaces from a large payload is slow and error-prone. A realistic API response can nest five levels deep, repeat the same object shape inside arrays, and include dozens of fields that nobody wants to type out manually. Worse, humans tend to write the interface they expect rather than the one the data proves: they mark every field required, assume every identifier is a number, and miss the one record in fifty where a value is null. A converter that studies the actual data makes none of those assumptions. It reads what is there, counts what repeats, and notices what is sometimes missing. The result is not a prettier guess but a description derived from evidence, which is exactly what a type is supposed to be.

Optional Fields: The Detail Most Converters Get Wrong

The single most valuable behaviour in this tool is optional field detection across arrays of objects. Real collections are uneven. In a list of users, most have a phone number and some do not. In a list of products, some carry a discount price and others never go on sale. If you convert only the first object in the array, every field looks required, and your code will confidently read values that are absent for half your records. By comparing all objects in an array, ModelMint marks any key missing from at least one record as optional, rendering it with a question mark. Your code then has to check before it reads, which is precisely the discipline that prevents the classic undefined-is-not-an-object crash in production.

The same cross-record comparison catches type drift. APIs evolve, backends are inconsistent, and different code paths populate the same field differently. One order may store its total as a number while a legacy record stores it as a formatted string. One event may set its payload to an object while another sets it to null. A careful converter responds with a union type, joining every observed possibility with a vertical bar. Unions can feel verbose at first, but they are the truth, and TypeScript narrows them beautifully at the points where you check them. Preferring a slightly longer, truthful type over a short, fictional one is the core design philosophy here.

Smart Naming for Nested Types

Generated code lives or dies by its names. Tools that emit Root, Root1, Root2, or a single giant inline type produce output nobody wants to keep. Readable generation names each nested object after its place in the structure: a profile contains a User, a user contains a UserAddress, and a list of line items contains an Item. Array keys are singularised, because an array of items is made of individual items, and categories resolve to a single Category rather than a plural that reads awkwardly as a type name. When two genuinely different shapes would claim the same name, a numeric suffix keeps them distinct instead of silently merging structures that should stay separate.

Naming also respects the root you choose. The root interface name is the one your team will import everywhere, so it should match your domain language: Product, Customer, Invoice, SearchResponse, or whatever the payload represents. Set it before you convert, and nested names build naturally from context. Keys that are not valid TypeScript identifiers — keys with spaces, dashes, or leading digits, which JSON happily allows — are safely quoted in the output, so unusual payloads still produce code that compiles without manual repair.

How to Use the Generated Types Well

Generation is the beginning, not the end, of good typing. Paste the output into a types file, then read it once with human eyes. Generation can tell you that a field is a string, but only you know whether that string is an email address, a URL, or an identifier that deserves a branded type. Consider tightening a few high-value fields: dates arrive as strings, yet converting them to a DateString alias documents intent; status fields often hold a small set of literals, and replacing string with a union of those literals gives you exhaustive checks. Keep the generated shape as the foundation, then refine the places where your domain knowledge adds information the data alone cannot provide.

Sample size matters too. Converting from one small example produces types for that example only. Converting from a large, representative response — ideally a full page of real results, including the awkward records — produces types you can trust. If an endpoint paginates, grab the largest page you can. If different variants exist, such as success and error envelopes, convert them separately and combine the results with a union or a discriminated check on a status field. And when the API changes, regenerate: keeping a saved sample of each important response in your repository makes refreshing its types a thirty-second habit rather than a archaeology project.

Generated interfaces pair naturally with runtime validation. Types protect you at compile time, but data crossing a network boundary can still surprise you at runtime, especially when a backend deploys without telling the frontend team. Many teams use the generated interfaces as the target shape for a validator, asserting that incoming data matches the type before the rest of the application trusts it. Even without a validation library, the interfaces make code reviews sharper: when a pull request changes a type, reviewers can see exactly which fields appeared, vanished, or changed, and ask whether the code that consumes them changed too.

Common Patterns You Will See in the Output

Arrays of primitives become simple typed arrays, such as string arrays for tags or number arrays for scores. Empty arrays become unknown arrays, an honest admission that the sample offered no evidence about the element type; add a better sample or annotate that field yourself. Deeply nested configuration objects unfold into a family of small interfaces rather than one enormous declaration, which keeps each type reusable — a shared Address shape, for instance, can describe both a billing address and a shipping address when the structures match closely enough for your codebase. Mixed arrays, rare but real, become arrays of unions, preserving every element kind the sample contained.

Numbers deserve one clarification. JSON has a single numeric type, so integers and decimals both become the TypeScript number type. If a field must be an integer in your domain, that constraint lives in your validation logic rather than in the type itself. Booleans are detected exactly, strings stay strings even when they look like dates or numbers, and nested arrays — matrices, grids, coordinate lists — become multi-dimensional array types automatically. Nothing is coerced, rounded, or reinterpreted: the conversion describes your JSON as it is.

Frequently Asked Questions

What does ModelMint convert, exactly?

ModelMint takes any valid JSON value — most usefully an object or an array of objects — and generates TypeScript interfaces that describe its shape. Strings become string, numbers become number, booleans become boolean, null becomes null, nested objects become named interfaces, and arrays become typed arrays such as string[] or OrderItem[]. The result is plain TypeScript you can paste straight into a project.

How does optional field detection work?

When your JSON is an array of objects, ModelMint compares every object in the array. A key that appears in some objects but not in others is marked optional with a question mark, for example nickname?: string. Keys present in every object stay required. This mirrors real API responses, where some records omit fields, and it saves you from adding the question marks by hand.

How are nested interfaces named?

Nested types get smart, readable names built from their parent and their key. Inside a root interface, a user object becomes User, and an address inside that user becomes UserAddress. Array keys are singularised first, so items becomes Item and categories becomes Category. If two different shapes would collide on the same name, ModelMint appends a number so every interface stays unique.

What happens when a field has different types in different records?

ModelMint builds a union. If one record has count as a number and another has it as a string, the field becomes count: string | number. If a field is sometimes null, null joins the union, for example string | null, so your code is forced to handle the missing-value case instead of discovering it at runtime.

Is my JSON uploaded anywhere?

No. ModelMint runs entirely in your browser. The JSON you paste is parsed and converted on your own device, nothing is sent to a server, and nothing is stored after you close the tab. That makes it safe for internal API payloads, staging responses, and sample data you would rather not paste into a hosted service.

Can I customise the output, rename the root type, or add documentation?

Yes. Set the root interface name to match your domain, such as Product, Customer, or ApiResponse, and toggle the export keyword, alphabetical key sorting, and JSDoc comments. With JSDoc on, each interface and field gains a short comment showing an example value from your data, which makes generated types easier to review in an editor.
